# Documentation rules

- Write for a technically capable stranger with no conversation history.
- Distinguish implemented, experimental, planned, and unsupported behavior.
- Keep quickstarts copyable and include prerequisites, expected output, verification, troubleshooting, and teardown where relevant.
- Link to the normative specification instead of duplicating rules that can drift.
- Use diagrams only when they clarify topology, sequence, or trust boundaries.
- Do not claim production readiness, certification, compatibility, or benchmark success without recorded evidence.
- Follow `WRITING.md` and update nearby stale statements while changing a document.
